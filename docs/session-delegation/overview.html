01三个思想

方案由三条线交汇而成:委派模型平级化 · 编排层上移预留 · Codex 生产验证。

思想一:委派 = 平级会话(不是受控子进程)

协调者
session-P┃血缘记录 执行A执行B执行C用户会话

执行单元互相平级、独立存活、GUI 可见可接管。parentSession 只是血缘记录，不是控制关系。类比:函数调用 → 邮件/会议。

思想二:编排上移(workflow 暂留,vibee 后期)

vibee 编排
(Run Graph)→ DSH 执行层
平级会话池

编排能力由 vibee 生态承接(wt-vibee 已在做)；本次不迁移，只把 DSH 执行面收敛成「会话」，让 flow 生态未来从 session 层直接接入。

思想三:Codex 生产验证

父 Threadspawn_session 子 Thread
(=完整 Session)→ 同一 ThreadStore

Codex run_codex_thread_interactive 证实:subagent = spawn 一个真 Session + 血缘边 + 来源标记 + 继承环境/策略。没有任何 Activation/ownedChildren/descriptor 机制。

02现状五机制:受控树的全套配套

subagent 的 continuation manager(continuation.ts, 1213 行)用五个互相咬合的机制实现「父拥有子」。每个机制解决一个真实问题——但问题本身是「受控」引入的。

机制解决什么问题复杂度来源session 栈下
① Activation 三态
running/waiting/settled		 父等子树时的中间驻留态(子跑完了、孙还在跑) 三态靠推导非维护；销毁时机锁内决定；进程本地崩溃即失 消失——无子树等待概念，父不驻留
② ownedChildren 图 父销毁前必须等子孙(作用域悬挂防护) 释放要全表扫描；语义是「等待链」；与投递耦合 消失——会话自治，孤儿靠产品策略
③ descriptor 冷恢复协议 崩溃后如何重建子(版本化持久契约) 版本协议治理；写入时机敏感；与授权咬合；丢消息不重放 消失——SessionHeader + requestHeader 现成，隐式 resume 免费
④ child-first drain 宿主关闭时有序释放森林(admission 仪式) 关闭与创建并发；scope 注册顺序逆向工程；取消 top-down 释放 child-first 消失——AgentRegistry 统一 dispose，持久会话下次 resume
⑤ 精确父授权 只有创建者能续写(实例级) 「精确实例」语义无法跨进程；双关卡封异步恢复窗口；网关双层栅栏 降级——开放续写，隔离靠 workspace；区别只留 MessageSource 归因

五机制为什么是一个整体

朴素问题: 父委派了子，后来还要发消息、拿结果
朴素实现: 子 = 普通 session，父直接发消息
三个安全前提把问题变复杂:
  前提A 只有父能继续子   → ⑤ 授权 + ③ descriptor(恢复时验证谁)
  前提B 父退子要清理      → ② ownedChildren + ④ drain
  前提C 崩溃后能恢复      → ③ descriptor + ① Activation(驻留容器)
拆掉任何一个，另外四个都失去意义 → 这就是「一个整体」的原因

五机制语义全部可以用 DSH 现成元数据设施重建——专用协议变成通用声明式元数据。

delegation 投影(替代 Activation 三态)

ProjectionDefinition<'delegation', DelegationState>
  init:  { status: 'idle', promptCount: 0 }
  apply: turn/start            → status: 'running'
         turn/end(completed)   → status: 'completed'
         turn/end(error)       → status: 'failed'
         assistant/message     → lastAssistantSeq = seq
  view:  { status, lastTurnEnd?, promptCount, lastAssistantSeq? }
  stateVersion: 1

  运行效果: 状态自动推导、自动持久(投影缓存)、
            变更自动推送 GUI(session/projection 帧)
            → 崩溃/重启后从日志重建，零进程本地状态

04收集约束:补上树的最后一个缺口

平级化拆掉树后，深度/资源/授权都有替代——唯独「等一组会话满足完成条件」没有。session_collect 用声明式谓词补上，但不恢复控制。

约束类型(并发原语的会话版)

约束语义≈ JS
wait: 'all'全部终态后返回Promise.all
wait: 'any'任一终态即返回Promise.race
wait: 'n'完成 N 个返回(其余继续)—
wait: 'first-failed'任一 failed 即返回—
on_failurecontinue / cancel-restallSettled / Abort
timeout_ms超时快照返回(不报错)race+timeout

调用形态

session_collect({
  root: 协调者 sessionId   // 或 tags: ['plan:p-42']
  wait: 'all' | 'n',  n: 2,
  on_failure: 'cancel-rest',
  timeout_ms: 300_000
}) → {
  satisfied: true,
  sessions: [{id, status, result}],
  elapsed_ms
}

边界克制(ASM-007)

collect 不做:依赖图(DAG)/调度/重试编排/工作流状态机 —— 那些留给 vibee 生态。

血缘分树数据一直都在(traceSession 免费)，只是「等树」从隐式运行时机制变成显式声明式策略。

未来 vibee 接入时，collect 是它可复用的执行原语——不会白做。

07待拍板决策(6 项)

全部已定案的问题见 spec 1.4(ASM-001~009)；以下 6 项仍需用户确认，P0 T-2 是唯一需要用户在场的任务。

决策 1:continuable 选项

选项 A(推荐)
send_message/list_agents 直接走 session API，续写开放，P4 一步收敛
选项 B
continuable 暂留旧实现(标记 deprecated)，新旧两套并存
推荐理由
避免两套语义并存(origin/授权/GUI 都分裂)；回归有全量测试兜底

决策 2:授权强度默认值

workspace(推荐)
同 workspace 可续写，与 GUI 现状一致，数据现成(header.cwd)
creator
仅创建者血缘链可续写(近似 subagent 语义，放宽为血缘链)
anyone
完全开放
注意
creator/anyone 只约束插件工具路径，subagent 工具路径保持 workspace 级(ASM-009)

决策 3:等待语义

单 session idle(推荐)
session.wait 只承诺该会话静默；等 N 个由协调者循环/collect 组合
整树静默
保留 whenIdle 子树语义——与平级模型自相矛盾(父不拥有孙)

决策 4:清理策略

三件套(推荐)
标记(~archived tags)+ 手动 + 超时扫描(可后置)
最简
只做标记+手动，废弃会话永久留在持久层

决策 5:结构化输出方案(ASM-004)

JSON 约定+校验重试(推荐)
prompt 注入"最终答案必须 ```json" + 结果侧解析校验；能力声明保持 true
保留强校验
在 subagent-session 里注入轻量捕获工具(不复活整套 subagent 机制)
影响
workflow/ralph 的 structured 场景回归(P3 T-15)

决策 6:tool-subagent-report 去留
